# joycon-poweroff

**把 Nintendo Switch 的 Joy-Con 和 Pro 手柄彻底关掉，恢复到出厂装运态，让它们在收纳时不再漏电。**

零依赖的 Python 3 脚本，直接读写 HID 设备 —— Linux 走 `/dev/hidraw`，Windows 用 `ctypes` 调 SetupAPI。不需要 `hidapi`，不需要编译，不动任何系统目录，不用装驱动。

[English](README.md) · [协议细节](#它到底做了什么) · [安全须知](#安全须知)

---

## 解决什么问题

Nintendo 没给手柄提供关机功能。按同步键或者放着不动，只是让它进入睡眠模式，电池照样漏——充满电的 Joy-Con 放一两周就没电了。

手柄其实**可以**通过蓝牙真正断电，用的是固件里为出厂运输预留的低功耗状态。这个脚本做的就是这件事，并且会回读确认写入真的生效了。

成功执行后，手柄会：

- 几乎不再耗电（实测收纳状态下的电池寿命是 **2–3 年**，不是几周）
- 按任何按键都无法唤醒
- 配对信息被清除

想再用它，插 USB 到 Switch，或者长按同步键重新配对。

## 快速上手

两个平台用同一个文件。先用手柄配对蓝牙：长按指示灯旁边那个小圆形的同步键，直到指示灯开始闪，然后在系统的蓝牙设置里完成配对。**用 USB 不行** —— 原因见下面[「安全须知」](#安全须知)。

### Linux

```bash
# 1. 下载脚本（就一个文件）
curl -O https://raw.githubusercontent.com/b1ghawk119/joycon-poweroff/main/joycon-poweroff.py

# 2. 确认能识别到手柄
sudo python3 joycon-poweroff.py --list

# 3. 预览将要发送的数据包 —— 这一步不会真的发任何东西
sudo python3 joycon-poweroff.py --dry-run

# 4. 执行
sudo python3 joycon-poweroff.py
```

### Windows

```powershell
# 1. 下载脚本
curl.exe -O https://raw.githubusercontent.com/b1ghawk119/joycon-poweroff/main/joycon-poweroff.py

# 2. 确认能识别到手柄（不需要管理员权限）
py -3 joycon-poweroff.py --list

# 3. 预览将要发送的数据包 —— 这一步不会真的发任何东西
py -3 joycon-poweroff.py --dry-run

# 4. 执行
py -3 joycon-poweroff.py
```

> Windows 上请用 `py -3`（Python 启动器）而不是 `python`，这样脚本才会跑在你预期的解释器上。Microsoft Store 版的 `python.exe` 也可以。

成功时的输出长这样：

```
目标：Joy-Con (R)  (/dev/hidraw3, bluetooth)

[1/6] 切 Simple HID 输入模式
[2/6] 点亮 4 个灯
[3/6] 清配对信息 (SPI 0x2000)
[4/6] 置装运低功耗标志 (SPI 0x5000 = 0x01)
[5/6] 回读校验
      SPI 0x5000 = 0x01  ✓
      SPI 0x2000 前 2 个配对槽已清除  ✓
      （只抽查了前 2 个槽，更靠后的记录没检查）
      0x05 主机列表状态 = 0x00（参考值，不作判据）
[6/6] 断开并断电

完成，手柄应已断电。
唤醒：插 USB 到 Switch，或长按 sync 键重新配对。
```

## 使用示例

### 列出已连接的手柄

```bash
$ sudo python3 joycon-poweroff.py --list
Joy-Con (L)            /dev/hidraw3  (bluetooth)
Joy-Con (R)            /dev/hidraw4  (bluetooth)
Pro Controller         /dev/hidraw5  (bluetooth)
```

输出里带总线类型，一眼就能看出手柄是走蓝牙还是 USB。USB 上的手柄会被标成 `[不支持]` 并拒绝操作。

### 只预览，不发送

```bash
$ sudo python3 joycon-poweroff.py --dry-run
```

把**将要**发送的每一个包逐字节打印出来，然后直接退出，不做任何写入。想确认命令序列再动手，用这个：

```
[3/6] 清配对信息 (SPI 0x2000)
      > 01 02 00 01 40 40 00 01 40 40 07
[4/6] 置装运低功耗标志 (SPI 0x5000 = 0x01)
      > 01 03 00 01 40 40 00 01 40 40 08 01
[5/6] 回读校验
      > 01 04 00 01 40 40 00 01 40 40 10 00 50 00 00 01
      > 01 05 00 01 40 40 00 01 40 40 10 00 20 00 00 01
      > 01 06 00 01 40 40 00 01 40 40 10 26 20 00 00 01
      > 01 07 00 01 40 40 00 01 40 40 05
      (dry-run，不校验)
[6/6] 断开并断电
      > 01 08 00 01 40 40 00 01 40 40 06 00
```

### 关闭单个手柄

```bash
sudo python3 joycon-poweroff.py
```

交互式引导，中间有一道确认：让手柄 4 个灯同时闪。**一定要盯着灯看** —— 如果 4 个灯不是同时闪，说明不是蓝牙连接，立刻取消。

### 同时连着多个手柄

脚本会问你要关哪一个：

```bash
$ sudo python3 joycon-poweroff.py
检测到多个 Nintendo 手柄：
  [1] Joy-Con (L)            /dev/hidraw3  (bluetooth)
  [2] Joy-Con (R)            /dev/hidraw4  (bluetooth)
选择要关闭的手柄 [1-3]: 2

目标：Joy-Con (R)  (/dev/hidraw4, bluetooth)
...
```

要关一整套，就一个一个跑。

### 无人值守 / 写进脚本

`--yes` 跳过所有交互确认。检测到多个手柄时它会拒绝自动选择，所以放进"只连一个手柄"的脚本里是安全的：

```bash
sudo python3 joycon-poweroff.py --yes
```

退出码：

| 退出码 | 含义 |
|--------|------|
| `0` | 手柄已断电，或 `--list` / `--dry-run` 正常完成 |
| `1` | 已中止，或未达成目标。原因会打印出来。**这不保证什么都没改** —— 发送 `0x06` 之后被中断、或写入结果不明，同样会返回 1。 |

### Steam Deck

在桌面模式下可用。脚本需要裸 HID 访问权限，所以要加 `sudo`：

```bash
# 在桌面模式打开 Konsole
curl -O https://raw.githubusercontent.com/b1ghawk119/joycon-poweroff/main/joycon-poweroff.py
sudo python3 joycon-poweroff.py
```

没有安装过程，也没有卸载过程 —— 删掉文件就等于完全移除。

## 它到底做了什么

每条命令都是一个 64 字节的 HID output report：

```
buf[0]     = 0x01        report ID
buf[1]     = 包序号 0..15
buf[2..9]  = 震动数据（固定值）
buf[10]    = 子命令
buf[11..]  = 参数
```

脚本按下面的顺序发送，每一步都先确认回复再继续：

| # | 子命令 | 参数 | 作用 |
|---|--------|------|------|
| 1 | `0x03` 设置输入报告模式 | `0x3F` | 切到 Simple HID 模式，减少读噪声 |
| 2 | `0x30` 设置玩家灯 | `0xF0` | 4 个灯全闪 —— **人工确认这确实是蓝牙连接** |
| 3 | `0x07` 重置配对信息 | — | 初始化 `0x2000` SPI 段（清除配对数据） |
| 4 | `0x08` 设置装运低功耗态 | `0x01` | 在 SPI `0x5000` 写入 `0x01` —— 低功耗标志 |
| 5 | `0x10` SPI flash 读取 | `0x5000`，长度 1 | 回读校验：必须是 `0x01` |
| 5 | `0x10` SPI flash 读取 | `0x2000`，长度 1 | 回读配对魔数：不能再是 `0x95` |
| 5 | `0x10` SPI flash 读取 | `0x2026`，长度 1 | 第二个配对槽做同样的检查 |
| 5 | `0x05` 查主机列表状态 | — | 查询内存里的主机列表（仅打印参考） |
| 6 | `0x06` 设置 HCI 状态 | `0x00` | 断开 → 手柄进入 HID OFF 并断电 |

**为什么 `0x07` 和 `0x08` 缺一不可。** 两条不是重复的，各自堵住一种唤醒途径：

- 只发 `0x08 01`：低功耗标志设上了，但固件只禁掉「随手一按就能唤醒」的按键。只要配对信息还在，长按某些键照样能唤醒它。
- 只发 `0x07`：配对信息清掉了，但低功耗标志没设，手柄仍是普通睡眠态，一两周照样没电。
- 两条都发：手柄进入 HID OFF，按键完全唤不醒。这才是真正的出厂态。

**为什么 `0x06` 很关键。** 低功耗标志是在**链路断开的那一刻**才生效的。发 `0x06 00` 就是主动触发这个断开，让手柄立刻断电，而不用等主机那边断蓝牙。

协议细节记录在 [Nintendo Switch 逆向工程笔记](https://github.com/dekuNukem/Nintendo_Switch_Reverse_Engineering)。

## 输出的含义

| 输出 | 含义 |
|------|------|
| `完成，手柄应已断电。` | **成功** —— 手柄已断电 |
| `SPI 0x5000 = 0x01  ✓` | 低功耗标志已回读确认 |
| `SPI 0x2000 前 2 个配对槽已清除  ✓` | 配对槽已确认清除 |
| `已中止，未发送断电命令。` | **已中止** —— 没有发送断电命令。但手柄**可能已被修改**：请看后续几行，它会区分「已收到确认的命令」和「可能已发出但未确认的命令」 |
| `✗ SPI 0x5000 = ...，不是 0x01。` | 校验失败，标志没写进去 |
| `⚠ 未能确认手柄已恢复标准输入模式。` | 无法确认输入模式已恢复 —— **请断开重连手柄**，否则按键可能失灵 |
| `✗ 这不是蓝牙连接（usb）。` | 不是蓝牙连接，已拒绝；USB 下无法让手柄断电 |

## 环境要求

- **Linux**：需要 `/dev/hidraw`（任何现代发行版，含 Steam Deck）。需要 root 权限，或有该手柄 `/dev/hidraw*` 节点读写权限的用户。
- **Windows 10 / 11**：不需要管理员权限，不用装驱动。用的是 `setupapi.dll`、`hid.dll`、`cfgmgr32.dll`、`kernel32.dll`，都是系统自带的。
- **Python 3.7 或更新版本** —— 没别的了。

不用 `pip install`，不用编译，不用装系统包。

## 安全须知

**这个脚本会写手柄的 SPI flash。** 这个操作和 Nintendo 出厂时做的是同一件事，正确使用是安全的 —— 但操作失误可能把手柄变砖。**风险自负。**

脚本的设计是「失败即安全」：

- **每一步都校验通过才走下一步。** `0x07` 和 `0x08` 必须返回 `0x80` 确认字节；SPI 回读必须同时匹配确认字节、回显地址**和**返回长度。任何一步不过，脚本就停下，**不会**发送 `0x06`。但这不等于「什么都没发生」：**回读失败并不能证明之前的写入没落盘**，所以中止时手柄仍可能已被修改。脚本结尾会如实列出哪些命令收到了确认、哪些可能已发出但未确认，而不是宣称一切照旧。
- **无条件拒绝 USB。** `0x06` 在 USB 下不生效，低功耗标志也不会触发，所以脚本会识别总线类型并拒绝 —— 在**发送任何东西之前**就退出，不发 `0x03`、不发 `0x07`、不发 `0x08`。任何模式下都没有绕过选项。在 USB 上继续只会清掉配对信息、写上一个永远无法生效的标志，比什么都不做更糟。
- **拒绝未知设备。** 只接受 5 个已知的手柄 PID。只是碰巧用了 Nintendo 厂商 ID 的设备会被跳过。
- **写入前复查设备身份。** 设备节点会被复用 —— `/dev/hidrawN` 的编号会回收，手柄也可能在检测到打开之间断开。脚本会确认打开的就是刚才枚举到的那一个，而不是把命令发给顶替它的设备。
- **所有退出路径都恢复输入模式。** 标准 HID 驱动不认 Simple HID 模式（`0x3F`），停在那个模式的手柄看着还连着，但按键会全部失灵。脚本在取消、出错和 Ctrl-C 时都会切回标准模式。
- **如实报告发生了什么。** 失败时它会区分「已收到确认的命令」和「可能已发出但未确认的命令」，而不是谎报成功。

动手前有两点要清楚：

1. **第 2 步盯着灯看。** 4 个灯必须同时闪。如果不是，说明不是蓝牙连接，请取消。
2. **Switch 会撤销这一切。** 主机每次连上手柄都会发 `0x08 00` 清掉标志。手柄一旦重新配对到 Switch，就恢复成普通睡眠行为。

## 已知局限

- **配对槽是抽查，不是全读。** `0x2000` 段里的配对记录按 `0x26` 字节重复，槽数不定；而协议规定单次 SPI 读取上限是 `0x1D` 字节 —— 读完整整 4 KB 需要约 141 次往返。脚本只检查前两个槽（覆盖当前配对和上一个配对），并在输出里明确说明。埋在更靠后的记录不会被发现。
- **`0x05` 主机列表查询只是参考信息。** 它会打印出来，但从不作为断电的判据，因为没有任何文档能证实 `0x07` 是否同时清掉手柄内存里的列表。拿它当门禁会在真机上造成假中止。
- **仅支持蓝牙。** USB 是被识别并在发送任何命令之前拒绝，不是绕过。
- **Windows 后端是实验性的，从未在真实手柄上测过。** 它是照着微软文档的 SetupAPI / HID 契约写的，重叠 I/O 部分有 71 条 mock 断言覆盖，设备发现和身份校验路径也在真机上跑通过（用的是非手柄设备）。但**从没在 Windows 上连过任何 Joy-Con、Pro Controller 或其它受支持的手柄**。具体未验证的有：真实枚举与父设备分组、报告长度、序列号是否可用、蓝牙写入与回复、SPI 回读、物理断电、以及恢复。第一次使用请先跑 `--dry-run` 并盯着指示灯。Linux 后端是测试更充分的那条路。
- **仅支持 Linux 和 Windows。** macOS 通过 IOKit 暴露 HID，本脚本没有实现。WSL2 看不到配对给 Windows 的手柄 —— Windows 的蓝牙栈在 WSL2 虚拟机里不可见。改用 Windows 的 Python 跑即可，在 WSL 终端里也能用：
  ```bash
  py.exe -3 "$(wslpath -w ./joycon-poweroff.py)" --list
  ```
- **本 README 作者未在真机上测试过。** 协议处理是逐字节对照公开的逆向笔记核对的，逻辑也有自动化测试套件覆盖 —— 但第一次使用仍然建议先跑 `--dry-run`，并盯着指示灯。

## 故障排查

**`没找到 Nintendo 手柄。`**
- 确认手柄是通过蓝牙连接的，不是 USB。
- 跑 `--list` 看看实际检测到了什么。
- 如果 `--list` 能看到手柄、正常运行时却看不到，可能是手柄在检测和打开之间断开了 —— 重连后重试。

**`没有权限打开 /dev/hidrawN`**
- 用 `sudo` 运行。或者写一条 udev 规则，给你的用户授予该手柄 hidraw 节点的访问权限。

**第 2 步 4 个灯没有同时闪**
- 不是蓝牙连接。取消，然后重新配对。这个检查存在的意义就是抓这种情况。

**`✗ 这不是蓝牙连接（usb）。`**
- 脚本在 USB 总线上找到了手柄，并在**发送任何东西之前**就拒绝了 —— 不发 `0x03`、不发 `0x07`、不发 `0x08`。这个拒绝发生在任何命令之前，所以这种情况下手柄确实未受影响。拔掉线，改用蓝牙连接；USB 下无法让手柄断电。
- 这个拒绝是刻意的，没有绕过选项。在 USB 上，脚本只能清掉配对信息、写上一个永远无法生效的低功耗标志，结果比不做更糟。

**取消之后按键没反应**
- 脚本本应自动恢复标准输入模式。如果它提示未能恢复，请断开重连手柄 —— 重连会重置模式。

**手柄自己又活了**
- 有东西重新连上了它。Switch 每次连接都会清掉低功耗标志。把它从所有设备上断开，再跑一次脚本。
